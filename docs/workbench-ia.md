# Luway 工作台信息架构与服务对象扩展方案

状态：设计中
日期：2026-09-23
范围：产品定位收敛、工作台信息架构、服务对象从客户扩展到员工与伙伴
关联：本文是 [Luway 路线图](roadmap.md) 登记的独立方案，设计细节只保留在本文；助理与本地运行见 [助理与桌面端本地运行实施方案](desktop-local-agent.md)

## 1. 定位

Luway 让企业拥有自己的 AI 员工，在客户、员工、伙伴常用的地方上岗；AI 办不了的事由人接住。

产品分三层，业务层是差异所在：

| 层 | 内容 |
| --- | --- |
| 引擎层 | Agent 运行时、知识库、MCP 工具、模型服务 |
| 连接层 | 渠道：网站挂件、Telegram、微信公众号、微信客服、企微／钉钉／飞书应用机器人、伙伴门户；以及 Luway 原生聊天 |
| 业务层 | 服务会话、队列与团队、转人工承接、内部协作、身份与数据范围、审批、报表与待补知识 |

三类服务对象共用同一套业务层：

| 服务对象 | 谁在提问 | 从哪里进来 | 谁来兜底 |
| --- | --- | --- | --- |
| 客户 | 外部客户 | 网站挂件、Telegram、微信客服等对外渠道 | 客服团队 |
| 员工 | 本企业员工 | 企微／钉钉／飞书机器人、Luway 原生聊天 | IT、人事、财务等职能团队 |
| 伙伴 | 经销商、代理商、供应商 | 伙伴门户、微信客服 | 渠道部、客户经理 |

个人效率类 AI（员工的个人助手）不在本方案范围内：属于组织的是 AI 员工，属于成员本人的是助理。

## 2. 概念

产品只有两个概念：会话承载谁在和谁说话，服务周期承载一件需要组织负责的事。

### 2.1 会话与服务周期

会话有三种形态：单聊、群聊、渠道会话。会话对参与者始终显示在一级栏或其渠道客户端。

会话中出现一件需要组织负责的事时产生服务周期，它有负责人或队列、内部协作和结束方式。周期按请求划分：上一个周期结束后，发起人再次提问时开启新周期，渠道会话与 Luway 内的单聊同一规则。收件箱是服务周期的视图，每行对应一条服务会话的当前周期：「全部」列出所有服务周期，「待处理」列出需要我动手的服务周期。

是否产生服务周期由入口和发起人身份共同决定：

- 入口是渠道或 AI 员工，各自声明服务哪几类对象（客户、员工、伙伴）。
- 发起人属于哪一类由身份识别决定：渠道访客默认是客户，关联到员工目录的是员工，绑定到伙伴组织的是伙伴。
- 发起人属于入口声明的服务对象时产生服务周期，否则只是聊天。该规则与首接待是 AI 员工还是真人无关。

由此，渠道会话的发起人天然是服务对象；成员私聊或 @服务对象不含本企业员工的 AI 员工是试聊；成员与助理的对话永远不产生服务周期。

同一条会话可以同时出现在两处，因为看的人不同：提出请求的人看到聊天，负责处理的人看到收件箱，两边是同一份消息。带服务周期的会话下文简称服务会话。

### 2.2 AI 员工与助理

归属决定执行位置与可见范围，两类 AI 的完整对照见助理方案。本方案只补充服务侧规则：

- AI 员工有服务对象和负责人。负责人维护它的知识、处理它答错的反馈。
- 助理属于成员本人，不能接待任何服务对象，与助理的对话不产生服务周期，不进入任何人的收件箱。助理在群里的可见范围按助理方案执行：主人把它带进群后，群成员可以使用它，并看到它在主人电脑上读取的内容。

### 2.3 服务周期的承载位置

| 会话 | 服务周期 | 承载位置 |
| --- | --- | --- |
| 渠道会话 | 每次请求一个周期 | 整条会话 |
| 成员单聊以本企业员工为服务对象的 AI 员工 | 每次请求一个周期 | 整条会话 |
| 成员单聊或 @服务对象不含本企业员工的 AI 员工 | 无，属于试聊 | 留在原会话，不进收件箱 |
| 同事单聊、群聊、与助理的对话 | 无 | 不进收件箱 |

### 2.4 转人工与请示

AI 办不了时有两种出路，区别是责任是否转移：

- **转人工**：交出责任，交给队列或团队，不点名到人；收件箱出现待领取，分配后成为某人的等我回复。真人之间的转交可以点名到人。
- **请示**：保持责任，向某个懂的人要一句事实或口径，拿到后自己回复；形式上是内部备注 @人。请示暂不实施，启动条件见暂缓事项。

### 2.5 渠道与转人工去向

渠道是服务对象联系 AI 员工的地方。渠道记录接待的 AI 员工、服务对象和办不了时的去向；网站、Telegram 等对外渠道固定服务客户，渠道的服务对象随员工 IM 渠道加入。Luway 原生聊天不作为渠道配置：成员直接单聊 AI 员工或在群里 @它。

Luway 内的单聊产生的服务会话不属于任何渠道，来源记为「单聊」。

AI 转人工的去向只能是团队或公共队列；AI 员工因停用或服务对象变化失去资格而退回负责的周期时，去向规则相同。按以下顺序确定：

1. 咨询分类对应的团队。
2. 渠道会话取渠道的失败去向；Luway 内的单聊取 AI 员工配置的「办不了交给谁」。
3. 以上均未配置时进入公共队列。

## 3. 数据显示在哪里

左侧一级栏是我参与的聊天，收件箱是我要处理的服务会话。

| 数据 | 显示位置 |
| --- | --- |
| 同事之间的群聊、单聊，含群里有人或 AI @我 | 一级栏群聊、单聊，显示 @ 标记与未读 |
| 我与 AI 员工、助理的对话，含试聊和我发起的服务请求 | 一级栏单聊 |
| 服务会话 | 处理人的收件箱「全部」 |
| 需要我动手的服务会话：等我回复、内部备注 @我、待领取 | 收件箱「待处理」 |

规则：

- 同一次提醒只出现在一个位置。群聊的 @ 属于沟通，不进收件箱；收件箱的「@我」只来自服务会话的内部备注。
- 提出请求的一方看到聊天，处理的一方看到收件箱，两边是同一条会话的同一份消息，不复制数据。
- AI 需要人接手时调用转人工，交给队列或团队；@ 只用于普通提醒，不用于转移责任。
- 消息可见范围按参与者在该服务会话中的角色决定：处理人看到内部备注，发起人看不到。

### 3.1 提出请求一方的体验

发起人在与 AI 员工的单聊中看到服务进度，接手的真人发言标注「代 <AI 员工> 处理」，周期结束后后续提问仍由 AI 员工首接待。

## 4. 工作台信息架构

```text
搜索
收件箱 3        待处理 ｜ 全部
AI 员工         AI 表现 ｜ 团队表现 ｜ AI 员工 ｜ 渠道 ｜ 知识库 ｜ 工具
通讯录          同事 ｜ 团队 ｜ 外部联系人 ｜ 我的助理
─ 群聊 ＋
─ 单聊 ＋
头像            工作状态 ｜ 设置
```

### 4.1 收件箱

- 服务对象筛选中的伙伴随伙伴服务台开放。

### 4.2 会话详情

- AI 转人工那一轮的处理过程（工具调用与结果）在时间线上不可查看；交接卡片补充查看该轮处理过程的入口。
- 侧栏按服务对象展示资料：员工显示部门与主管，伙伴显示等级与客户经理。

### 4.3 通讯录与聊天

- 通讯录只用于找人：同事、团队、外部联系人、我的助理。成员账号、角色与邀请在设置中维护。

## 5. 模型影响

以下改动在对应阶段实施：

| 事项 | 内容 |
| --- | --- |
| 服务对象 | 渠道记录服务对象，随员工 IM 渠道加入；发起人类别由身份识别确定 |
| 员工身份 | 从企微、钉钉、飞书通讯录同步员工目录（外部编号、姓名、部门、直属主管），机器人渠道的发起人关联到目录成员 |
| 伙伴身份 | 伙伴组织（名称、等级、外部编码、负责的客户经理或团队）与伙伴成员，路由可按伙伴指定客户经理，优先于渠道路由 |
| 身份范围注入 | MCP 工具中决定数据范围的参数（员工编号、伙伴编码）由服务端按发起人身份注入，模型不可见、不可改 |

## 6. 阶段

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| C 员工 IM 接入 | 渠道服务对象；员工目录同步、身份范围注入；钉钉 Stream 机器人渠道，其后飞书长连接、企微智能机器人长连接；再按 MCP 查询、身份系统执行与主管审批推进 | 审批依赖 Agent P1.5 |
| D 伙伴服务台 | 伙伴组织与成员、身份绑定、按伙伴路由、ERP 查询类工具；其后主动通知与伙伴门户 | C 中的身份范围注入；需要一个开放业务系统查询接口的真实客户 |

Luway 单聊的发起人是已登录成员，身份无需同步；员工目录同步只服务 IM 机器人渠道。阶段 C 与客服闭环的 P2 事项、其余渠道并行推进。

三家 IM 的机器人都提供免公网回调的长连接方式，适合自托管部署。企微智能机器人由非超级管理员创建时只返回加密 userid，查询部门需要另建自建应用。

阶段 C 验收时需回答是否需要工单：IT 报修、人事办理等场景若服务会话与交接卡片不足以表达跨部门办理，启动工单评估。

## 7. 暂缓事项

| 事项 | 启动条件 |
| --- | --- |
| AI 向同事请示：AI 保持负责，向专家要一句事实或口径，答案沉淀为知识候选 | 员工服务台交付后，且知识缺口显示大量问题只差一句口径 |
| 伙伴门户中的群协作与受管访客 | 伙伴服务台出现群协作需求 |
| 工单 | 阶段 C 验收结论需要工单，或客服侧服务会话与交接卡片不足以表达跨部门办理；共性故障批量通知先于完整工单 |
| WorkBuddy 桌面端连接：作为助理的备选执行器，或把 Luway 上架为其连接器 | 前者需要 WorkBuddy 桌面端开放 ACP（同一底座的 CodeBuddy CLI 按 P4 本机 Agent 的条款核实接入），后者需要开放 API 与员工服务台 |

## 8. 不做的事

- 不做以工单为中心的事项工作台，不把首页改成事项三栏。
- 不按人数或公开与否把会话拆成讨论组与私信，保持现有单聊与群聊，与 AI 员工、助理的单聊沿用多对话模型。
- 不做企业级模块开关。
- 不建设通用规则引擎与自定义字段工厂。
